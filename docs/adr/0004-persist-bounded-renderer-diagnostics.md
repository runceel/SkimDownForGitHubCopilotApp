# 0004: renderer 診断を上限付き成果物として永続化する

- Status: Accepted
- Date: 2026-07-30
- Supersedes: なし
- Superseded by: なし

## Context

renderer は入れ子のブラウザー frame で動き、拡張プロセスから DOM、script load、
未処理例外を直接観察できない。frame が起動前に失敗すると、通常の通信経路も成立せず、
ユーザーには空の preview だけが残る。

拡張のホストログは ephemeral であり、プロバイダ再接続や事後調査の時点には失われる。
一方、無制限な永続ログは、ディスク使用量と内容の管理を難しくする。

## Decision

renderer とシェルは、他の renderer 資産より早い段階から起動状態とエラーを収集し、
成立している loopback 診断経路を通じて拡張プロセスへ報告する。

診断は `$COPILOT_HOME` 配下のリポジトリ外成果物へ永続化し、件数に上限を設けて新しい記録を
優先する。失敗だけでなく正常起動時に選ばれた通信経路も記録し、古い URL、起動失敗、
互換レイヤー失敗を区別できるようにする。

診断は best effort とし、診断の失敗で canvas を停止させない。Markdown 本文は記録しない。

## Alternatives considered

- **ephemeral なホストログだけを使う**: 最も必要な事後調査時に証拠が残らないため採用しない。
- **frame を拡張プロセスから直接検査する**: process と browser frame の境界上できない。
- **診断を無制限に追記する**: 長期運用で不要なデータが増え続けるため採用しない。
- **失敗時だけ記録する**: 起動経路自体が古い場合と、起動後に壊れた場合を比較できないため採用しない。

## Consequences

### Positive

- 空の preview を、再現中でなくても原因別に調査できる。
- 正常時との比較により、host 環境や通信経路の差を確認できる。
- リポジトリへ診断ファイルを混入させない。

### Negative

- 上限を越えた古い診断は残らず、完全な監査ログにはならない。
- 診断スキーマと機密情報を含めない方針を維持する必要がある。

### Follow-up

- 新しい診断項目は、問題の切り分けに必要か、Markdown 本文や不要な個人情報を含まないかを
  確認してから追加する。
