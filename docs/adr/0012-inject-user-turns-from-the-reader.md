# 0012: 読み手の指示を、ユーザー操作に限ってセッションへ注入する

- Status: Accepted
- Date: 2026-08-03
- Supersedes: なし
- Superseded by: なし

## Context

この拡張は、エージェントが生成した Markdown と既存の Markdown を canvas で読むための
読み取り専用 UI である。ホストからの canvas 入力とアクションで表示対象を受け取り、
セッション中に編集された Markdown を自ら収集する。しかし情報の流れはセッションから
canvas への一方向であり、読んでいる箇所を起点にエージェントへ働きかける経路がない。

その結果、読み手が疑問を持った時点で、対象文書の名前、位置、引用を chat 入力欄へ
手作業で写す必要がある。読書面とエージェントが同じウィンドウにあるという canvas の
構造上の利点が、この一点で失われている。

一方、拡張はホストセッションへ参加した時点でセッションへメッセージを送る能力を持つ。
つまりこの経路の追加は、新しいホスト機能ではなく、拡張が持つ権限を UI へ露出するか
どうかの設計判断である。

同時に、これは拡張にとって初めての**外向き**の作用でもある。これまで拡張は、ホストと
ユーザーからの入力を受け取る側にしかいなかった。エージェントを起動できるということは、
そのエージェントが文書を更新し、その更新が canvas に反映され、さらに次の送信を誘発する
という循環が構造的に可能になることを意味する。また、送信される文面には、信頼しない
Markdown 由来のテキストが引用として含まれ得る。

## Decision

読み手が canvas 上で行った**明示的な操作に限り**、拡張はホストセッションへ user turn を
1 件注入する。canvas は指示の起点であり、文書やリポジトリを書き換えない。Markdown の
編集は引き続き非責務であり、変更を行うのはセッション側のエージェントである。

この経路には次の不変条件を課す。

1. **送信はユーザーの明示操作からのみ開始する。** ファイル監視、イベント配信、ホストからの
   canvas アクション、再接続処理など、ユーザーの操作を伴わない経路から送信してはならない。
   これは循環を構造的に成立させないための境界であり、利便性より優先する。
2. **送信対象の文書同一性は拡張プロセス側の選択状態を正とする。** クライアントが送る
   ファイルパスや文書識別子を、そのまま送信対象として信頼しない。既存のローカルファイル
   操作と同じ許可範囲の中に留める。
3. **拡張はユーザーの意図を足さない。** 拡張が文面へ加えてよいのは、要求の出所と読書対象の
   提示に限る。ユーザーが書いていない依頼や指示を代わりに書かない。
4. **入力には上限と受付頻度の境界を課す。** 質問文と引用にそれぞれ長さ上限を設け、
   送信の受付頻度も制限する。境界を越える要求は拒否する。
5. **質問文と引用本文を診断やログへ記録しない。** 既存の「診断へ Markdown 本文を記録しない」
   境界を、この経路にも同じ強さで適用する。

引用に含まれる本文は信頼しない入力として扱い、送信する文面の中で引用であることが
明確に区別される形にする。この経路は、既存の loopback API と同じ capability、
同一 origin のブラウザー要求境界、JSON 要求の制約の上に置く。

## Alternatives considered

- **一方向のまま維持する**: 実装も信頼境界も最小に保てるが、読書面とエージェントが同一
  ウィンドウにあるという canvas 固有の利点を活かせない。この拡張が standalone の読書
  アプリに対して持つ差別化が失われるため採用しない。
- **canvas アクションとしてホストへ露出する**: エージェント側から呼べる形にすると、
  ユーザー操作を伴わない送信が可能になり、不変条件 1 を守れない。採用しない。
- **canvas から別のセッションを生成して問い合わせる**: 新しいセッションの生成と寿命管理を
  読書 UI が背負うことになり、責務として重い。またセッション文書を別セッションへ
  漏らさないという既存の隔離とも整合しない。採用しない。
- **引用本文をサーバー側で文書と照合してから送る**: 表示された文章と Markdown 原文は一致
  しないため、照合は成立しない。長さ上限、引用の明示、ユーザー操作の必須化で代替する。
- **編集操作まで canvas に持たせる**: 読み取り専用という責務を崩し、リポジトリ内容の暗黙的な
  変更を招くため採用しない。

## Consequences

### Positive

- 「読む、気づく、指示する」が同じ画面で完結し、読み手が文脈を手作業で写す必要がなくなる。
- 読書対象と引用が構造化された形でエージェントへ届くため、指示の曖昧さが減る。
- 送信がユーザー操作に限定されるため、自動送信による循環が構造的に発生しない。
- 読み取り専用という責務が保たれ、変更の実行主体はエージェントのままである。

### Negative

- 拡張が初めて外向きの作用を持つため、認証、入力境界、頻度制限を新たに維持する必要がある。
- 引用本文は表示側に由来し、拡張プロセスは内容を検証できない。信頼しない入力として扱う
  責任が文面の構成側に残る。
- 送信後の応答は canvas ではなくセッション側に現れるため、読み手の視線が 2 か所に分かれる。

### Follow-up

- `docs/architecture.md` の責務、通信、不変条件を、この外向き経路を含む現状へ更新する。
- 今後この経路へ新しい入力（節の指定、複数引用など）を足すときも、同じ不変条件を適用する。
- 送信経路の回帰テストを、既存の loopback API のセキュリティテストと同じ場所で維持する。
