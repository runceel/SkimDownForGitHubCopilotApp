# 0014: 可観測性と想定外の非同期失敗で読書 UI を停止させない

- Status: Accepted
- Date: 2026-08-05
- Supersedes: なし
- Superseded by: なし

## Context

拡張プロセスは canvas の実体である。プロセスが終われば、読書 UI も、loopback サーバーも、
ファイル監視も同時に失われる。ユーザーから見えるのは空のパネルだけで、原因は
ホストのログを追わなければ分からない。

拡張がホストへログを送る経路は JSON-RPC の要求であり、二通りに失敗する。呼び出し時に
throw する場合と、返された promise が後から reject する場合である。同期的な例外処理は
前者しか扱えない。後者は unhandled rejection となり、Node の既定動作でプロセスが終了する。

ホストが受理するログ severity は固定の集合であり、範囲外の値は無視されずに拒否される。
つまり「記録の付随情報が 1 つ合わない」だけで要求が reject され、そのまま canvas 全体の
停止まで増幅し得る。ADR 0004 は診断について「診断の失敗で canvas を停止させない」と
定めているが、この不変条件は診断経路に限らず、可観測性そのものと、await されない非同期処理
一般に必要である。

一方で、すべての失敗を一律に飲み込むと、起動できていない拡張が「生きている」ように見え、
ホストが異常を検知できなくなる。

## Decision

可観測性の失敗と、セッション参加後に発生した想定外の非同期失敗は、拡張プロセスを
終了させない。

- ログ送出は呼び出し側から見て決して失敗しない。ホストが受理する severity へ正規化した
  うえで送り、同期例外と promise の reject の両方を送出側が吸収する。
  ログのために再試行を重ねない。
- await されない promise の reject と捕捉されない例外は、プロセス境界で受け止め、
  理由を記録したうえで実行を継続する。記録先はホストのログ経路とし、それが使えない場合の
  フォールバックは stderr とする。stdout は JSON-RPC 専用であり使わない。
- 例外は起動である。セッションへ参加できない場合は継続しても canvas が存在しないため、
  失敗を隠さず、非ゼロ終了でホストへ委ねる。

## Alternatives considered

- **ログ送出の堅牢化だけ行う**: 既知の失敗は塞げるが、await されない処理は他にもあり、
  同じ形の停止が別経路で再発するため採用しない。
- **プロセス監視と再起動に任せる**: 再起動のたびに canvas の実行時状態と読書位置が失われ、
  ユーザーから見た可用性は回復しないため採用しない。
- **すべての失敗を一律に飲み込む**: 起動不能な拡張が正常に見え、ホストが異常を
  検知できなくなるため採用しない。
- **ログ失敗時に再試行を続ける**: 記録のために本来の処理を妨げる可能性があり、
  ログの価値に見合わないため採用しない。

## Consequences

### Positive

- 記録経路の不整合、ホスト側のスキーマ変更、切断など、可観測性の問題が読書 UI を
  巻き込まなくなる。
- 想定外の非同期失敗が発生しても、原因が記録として残り、ユーザーは読書を続けられる。
- 起動失敗は従来どおりホストから異常として観測できる。

### Negative

- 捕捉されない例外の後も実行を続けるため、内部状態が壊れたまま動作する可能性がある。
  記録を必ず残すことと、起動失敗を例外とすることで影響範囲を限定する。
- 停止しなくなる分、問題が記録の中に埋もれやすくなる。severity を正しく使い分ける必要がある。

### Follow-up

- 新しい非同期処理を追加するときは、失敗経路が記録されるかを確認する。
- ログ呼び出しに新しい付随情報を足すときは、ホストが受理する値域を越えないことを確認する。
