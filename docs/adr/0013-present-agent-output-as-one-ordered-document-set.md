# 0013: エージェントの成果物を、順序付きのドキュメントセット 1 つとして提示する

- Status: Accepted
- Date: 2026-08-10
- Supersedes: なし
- Superseded by: なし

## Context

エージェントが読み手へ Markdown を渡す経路は、これまで 1 文書単位だけだった。

- `show_markdown` はインライン文書を 1 件登録する。複数回呼ぶと、すべてが
  「Markdown displayed by the agent」という 1 つのグループへ更新時刻順に積まれる。
- `open_path` はファイル 1 件かフォルダー 1 つを開く。フォルダーを渡すと、
  今回の成果物ではない `.md` まで同じ扱いで並ぶ。

どちらも「今回作ったのはこの 3 本で、この順に読んでほしい」を表現できない。
読み手は、どれが今回の成果物なのか、どこから読み始めればよいのか、
どこまで読めば終わりなのかを、サイドバーの並びから判断できない。

一方でこの拡張は読み取り専用であり、セッション文書はメモリが既定、永続化は opt-in で
期限付きという制約を持つ（ADR 0010）。またローカルファイル操作は許可された範囲に限られ、
クライアントが送るパスを信頼しない（ADR 0007 / 0012）。新しい提示概念は、
これらの境界を緩めずに載せる必要がある。

さらに、成果物はディスク上のファイルとして存在する場合と、まだファイルになっていない
草案として存在する場合の両方がある。片方しか受け取れない提示概念は、
実際の使われ方の半分を取りこぼす。

## Decision

**ドキュメントセット**を導入する。セッションが持つ、順序付きで名前を持つ提示単位であり、
ディスク上のファイル項目とインライン項目を混在できる。

この概念には次の性質を課す。

1. **セッションが持てるセットは常に 1 つである。** 新しいセットの提示は前のセットを
   置き換える。積み上げないため、「今回の成果物」が常に一意に定まる。
   セットの同一性はセッション内で安定したセット ID であり、`instanceId` では引かない。
2. **セットは本文の第 2 の保管場所ではなく、提示順を表す参照の並びである。**
   インライン項目の本文は既存のインライン文書として保持し、セットは所属を示す印だけを
   持つ。これにより本文の件数と byte 上限、永続化と期限、消去、リモートコンテンツの
   同一性、質問時の本文添付という既存の経路をそのまま共有できる。セット差し替え時に
   取り除くのは、前のセットに属していたインライン文書だけである。
3. **セットは「このセッション」ソースの先頭グループとして、指定順に並ぶ。**
   他のグループ（成果物、編集した文書、インライン、チェックポイント）からは重複を除く。
   セットは読む順であって更新順ではないため、このグループに時刻を表示しない。
4. **読めない項目は提示全体を失わせない。** 存在しないファイルや Markdown 以外の項目は
   セットから除外し、呼び出し元へ除外理由とともに報告する。1 件の誤りで
   残りの成果物が読めなくなる方が、読み手にとって損失が大きい。
   すべての項目が読めない場合だけ、空のセットを見せずに要求を拒否する。
5. **セット内の移動は方向だけを受け取る。** クライアントは前後のどちらへ動くかだけを送り、
   移動先は拡張プロセス側の一覧と選択状態から解決する。クライアントが送るパスや
   文書識別子を移動先として信頼しない。移動は端で止まり、回り込まない。
6. **セットの提示は user turn を送らない。** 外向きの経路は ADR 0012 の質問だけであり、
   ホストからの canvas アクションを起点に増やさない。

セットの保存形式は既存のセッションレジストリに追加するフィールドとし、
未知フィールドを落とす正規化に載せることで、保存済み履歴の schema version を上げない。
旧形式の履歴を、この機能の追加だけで無効化しない。

## Alternatives considered

- **`show_markdown` を複数回呼ぶ運用で足りるとする**: 実装は増えないが、順序と範囲が
  読み手に伝わらないという問題がそのまま残る。この ADR が解こうとしている課題そのものを
  解かないため採用しない。
- **セットを複数保持し、履歴として積み上げる**: 「前回の提示も見たい」に応えられるが、
  どれが今回の成果物かという一意性が再び失われる。加えて、セット単位の寿命、上限、
  消去 UI を新たに背負う。読み手が過去の文書へ戻る手段は既存のグループが提供しており、
  重複するため採用しない。
- **セットの本文を独立した保管場所へ持つ**: セット専用の上限や期限を設計できるが、
  永続化、期限切れ、消去、リモートコンテンツ同一性の経路が二重化する。
  ADR 0010 の境界を 2 か所で守り続ける必要が生じるため採用しない。
- **読めない項目があれば提示全体を拒否する**: 呼び出し元の誤りを早期に伝えられるが、
  典型的な誤り（パスの綴り、まだ書き出していないファイル）で成果物全体が読めなくなる。
  除外して報告する方が読み手の損失が小さいため採用しない。
- **移動先の文書識別子をクライアントから受け取る**: 実装は単純だが、
  不変条件（クライアントが送るパスを信頼しない）を破る。採用しない。
- **セットの端で回り込む**: 循環できる方が操作は軽いが、どこで読み終わったのかが
  分からなくなる。「範囲を伝える」という目的に反するため採用しない。
- **セットを明示的に消すアクションを足す**: 置き換えとセッション履歴の消去で足りる。
  外向きでない操作を増やす利得が小さいため採用しない。

## Consequences

### Positive

- エージェントが「今回の成果物」を、範囲と順序を含めて 1 回で提示できる。
- 読み手はサイドバーの先頭とツールバーの位置表示から、読む対象と残りを把握できる。
- ファイルと草案を混ぜられるため、書き出し済みかどうかで提示手段を変えなくてよい。
- 本文の保管を既存のインライン文書へ寄せたため、永続化と消去の境界が 1 か所に留まる。
- 保存形式の schema version を上げないため、保存済み履歴を無効化しない。

### Negative

- 「このセッション」ソースに、他と並び方の異なるグループが 1 つ増える。
  読み手はグループごとに順序の意味が違うことを理解する必要がある。
- セットを積み上げないため、前のセットは置き換えで失われる。個々の文書は他のグループに
  残るが、前回の提示順は残らない。
- セット項目の実体が後から消えると、サイドバーと位置表示から静かに減る。
  読み手には除外の理由が見えない。

### Follow-up

- `docs/architecture.md` の同一性、保存モデル、不変条件を、この提示単位を含む現状へ更新する。
- 今後セットへ新しい項目種別を足すときも、本文の保管を既存経路へ寄せる方針を維持する。
- 提示、置き換え、除外、移動の回帰テストを、既存の loopback API のテストと同じ場所で維持する。
