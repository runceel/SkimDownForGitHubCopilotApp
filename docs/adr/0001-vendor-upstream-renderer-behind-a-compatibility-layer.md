# 0001: 上流 renderer を互換レイヤーの背後で利用する

- Status: Accepted
- Date: 2026-07-30
- Supersedes: なし
- Superseded by: なし

## Context

SkimDownForWindows の Markdown 読書体験には、サニタイズ、コード表示、数式、図、
文書内検索など、相互に依存するレンダリング挙動がある。canvas 向けに同じ機能を
再実装または fork すると、上流との挙動差と保守負担が継続的に増える。

一方、上流 renderer は WebView2 のホスト契約を前提とする。GitHub Copilot app 自体も
WebView2 上で動くため、renderer が期待するホスト名はすでに app に占有されている。
実環境では、ホスト object とその WebView2 接点がともに non-configurable であり、
再定義と host object の置換は失敗した。一方、既存 WebView2 object の必要な接点を
適合させる方法は成立した。strict mode の単純代入は起動を中断することも確認された。

## Decision

renderer 本体、スタイル、ベンダー資産は、採用した上流リビジョンからバイト単位で
ベンダリングし、ローカル変更を加えない。canvas 固有の差異は、上流が期待する
ホスト契約を提供する独立した互換レイヤーと、外側のシェルで吸収する。

互換レイヤーは、ホスト名が自由に置換できると仮定しない。実行環境のプロパティ特性を
確認し、置換できない場合も既存ホストを壊さず契約を満たせる段階的フォールバックを使う。
どの適合方法が成立したかは、frame 外から診断できる状態にする。

## Alternatives considered

- **canvas 専用 renderer を再実装する**: 上流との機能差と二重保守が恒常化するため採用しない。
- **ベンダリング後の renderer を直接変更する**: 更新時の差分追跡が難しく、
  「上流を再コピーして追従する」という保守モデルを壊すため採用しない。
- **ホスト契約を単純代入で上書きする**: 実際の WebView2 host では置換不能であり、
  起動不能になるため採用しない。

## Consequences

### Positive

- 上流の改善を、明確なリビジョン単位の再コピーで取り込める。
- canvas 固有コードと Markdown レンダリング規則の責務が分離される。
- 実ブラウザー host の制約へ適合しつつ、上流 renderer の契約を維持できる。

### Negative

- 互換レイヤーは起動経路の重要コンポーネントとなり、上流のホスト契約変更へ追従が必要になる。
- ベンダー資産へ緊急修正を直接入れられず、上流修正と再ベンダリングが必要になる。

### Follow-up

- ベンダリング更新時は、対象資産が選択した上流リビジョンとバイト単位で一致することを確認する。
- 上流のホスト接点が増えた場合は、renderer を変更せず互換レイヤーの契約を更新する。
